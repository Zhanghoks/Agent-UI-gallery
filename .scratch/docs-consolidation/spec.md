# Spec：整理设计文件与整体架构文档

前置：`.scratch/gallery-foundation/spec.md` 已实现（基座重构、目录生成、atoms 边界与依赖校验）。本 spec 只整理文档与术语，不改变运行行为。

## Problem Statement

我在几轮讨论中陆续写了架构文档、ADR 和 spec，现在它们互相重叠、口径不一：架构文档同时混着「最初的计划」和「已经落地的现状」（v1、v2 叠加，命名如 `gen-index`、`foundry.config.ts` 已与实际不符，靠各 ADR 末尾的「实现补充」打补丁）；ADR 的状态都还写「提议」，但其中一部分已经实现；README、架构文档、ADR 之间对同一件事（目录结构、命令、分界规则）各写一遍；项目没有术语表，「组件 / primitive / atom / gallery 组件 / registry / foundation」在不同文档里含义漂移；ADR 编号与文档模板不一致；文档里引用的路径和命令没有任何东西保证它们真实存在。别人（或几个月后的我）很难一眼看出「现在到底是什么样、接下来要做什么、为什么这样定」。

## Solution

把文档整理成职责清晰、互不重复的一套：一个描述「现状」的架构文档、一份术语表、一组状态准确的 ADR、一份单独的路线图（尚未实现的设计），加一个文档入口索引；README 只讲怎么用，不再重复架构。并新增一个「文档一致性检查」命令：文档里引用的路径、npm 命令、脚本名与真实仓库不一致就报错，让文档不会再悄悄过期。

## User Stories

1. As a 维护者，I want 一份只描述「现在是什么样」的架构文档，so that 我不用在计划和现状之间来回分辨
2. As a 维护者，I want 尚未实现的设计（事件协议、组件受控化、画廊扩展点）集中在一份路线图里，so that 我知道下一步做什么、做到哪了
3. As a 维护者，I want 路线图中每一项都标明状态（未开始 / 进行中 / 已完成）和对应的 ADR，so that 进度一目了然
4. As a 维护者，I want 每份 ADR 的状态准确（已采纳 / 提议中 / 已被取代），so that 我能信任它
5. As a 维护者，I want 已实现的 ADR 把「实现补充」并入正文，so that 不用读两遍才知道最终决定
6. As a 维护者，I want 每份 ADR 保持「背景 / 决定 / 后果 / 备选」这一固定结构，so that 快速对比
7. As a 维护者，I want ADR 编号格式与文档模板一致并稳定，so that 引用不会失效
8. As a 维护者，I want 一份术语表定义组件库里的核心名词，so that 所有文档和代码评审用同一套词
9. As a 维护者，I want 术语表明确 atoms 与 gallery 组件的区别与依赖方向，so that 新组件放对位置
10. As a 维护者，I want 术语表区分「受控组件」和「Demo」，so that 之后改造组件时不产生歧义
11. As a 维护者，I want 术语表列出「避免使用的说法」（如把 gallery 组件叫 primitive），so that 文档不再漂移
12. As a 新贡献者，I want 一个文档入口索引，so that 知道先读哪份、每份讲什么
13. As a 新贡献者，I want README 只讲安装、命令、新增组件的流程和 atoms/gallery 规则，so that 五分钟内能上手
14. As a 新贡献者，I want README 指向架构文档而不是复制它，so that 只需要维护一处
15. As a 新贡献者，I want 架构文档里有一张当前目录树，so that 能对照真实仓库
16. As a 新贡献者，I want 架构文档说明数据如何流动（meta → 目录 → 画廊 / registry），so that 明白新增组件后发生了什么
17. As a 新贡献者，I want 架构文档列出所有校验规则及其含义，so that 构建报错时知道怎么改
18. As a 维护者，I want 已完成的 spec 保留但标注为已完成，so that 我能追溯当初的需求
19. As a 维护者，I want 各文档里对命令、路径、脚本名的引用是真实存在的，so that 照着文档做不会失败
20. As a 维护者，I want 文档检查在 README 命令表与 `package.json` 的脚本不一致时报错，so that 命令表不会过期
21. As a 维护者，I want 文档检查在引用了不存在的路径时报错并指出文档与行号，so that 能快速修正
22. As a 维护者，I want 文档检查确认每份 ADR 都有编号、标题和状态，so that 索引不缺项
23. As a 维护者，I want 文档检查确认入口索引列出了所有 ADR，so that 新增 ADR 时不会漏登记
24. As a 维护者，I want 文档检查允许历史性叙述（例如「原名 gen-index」）通过显式标记豁免，so that 不因说明沿革而误报
25. As a 维护者，I want 文档检查能在 `npm test` 中一并运行，so that 提交前就能发现文档漂移
26. As a 之后的开发者，I want 上游（Beautiful UI）来源与许可说明保持在单独的说明文档里并被索引，so that 合规信息不会丢
27. As a 之后的开发者，I want 文档里明确「哪些是占位值」（库名、registry 地址），so that 不会误以为已定稿
28. As a 之后的开发者，I want 已知的死代码和待清理项在架构文档里有一节，so that 不会误当成有用代码

## Implementation Decisions

- **文档职责划分**（互不重复）：
  - 架构文档 = 现状（as-built）：目标、分层、目录树、数据流、校验规则、命令、占位值、已知待清理项。
  - 路线图 = 尚未实现的设计：事件协议、组件受控化、画廊外壳扩展点，以及后续的组件替换计划；每项含状态与对应 ADR。
  - ADR = 单项决策：状态、背景、决定、后果、备选；已实现的将实现补充并入正文；被后来决定改变的旧结论标注「已被取代」并指向新 ADR。
  - 术语表 = 项目的领域词汇（单上下文，位于仓库根）。
  - README = 用法：安装、命令、新增组件流程、atoms/gallery 规则；引用而不复制架构。
  - 入口索引 = 列出上述所有文档及一句话说明，并登记全部 ADR。
- **术语表内容**：至少定义 atom、gallery 组件、meta、目录（catalog）、registry、foundation、harness、scenario、受控组件、Demo、origin（upstream/own）、category；并给出应避免的近义说法。术语表是唯一的定义来源，其他文档使用同一词汇。
- **ADR 处理**：现有 ADR 逐份核对实现状态：001–007 已实现（采纳），008、009 仍是提议并归入路线图；编号采用与文档模板一致的四位格式并一次性改名；文档内的交叉引用同步更新。
- **架构文档改写原则**：以真实仓库为准重写，去掉 v1/v2 的计划口吻；分层依赖方向、校验规则清单、命令表以当前实现为准；「占位值」与「已知待清理项」（未被引用的遗留组件等）单独成节。
- **完成的 spec**：保留在 issue tracker 目录中，状态改为已完成，不删除。
- **文档一致性检查**：一个命令，输入仓库根目录，输出问题列表（文档、位置、说明）；无问题则退出码为 0。检查项：
  - 文档中以行内代码形式出现的、看起来是仓库路径的引用必须真实存在；
  - README 命令表中的每条 npm 命令必须存在于包的脚本中，反之包中面向使用者的脚本也应在命令表中；
  - 每份 ADR 具备编号、标题、合法状态；
  - 入口索引登记了全部 ADR 与文档；
  - 支持显式豁免标记，用于沿革性叙述、生成文件路径、示例路径。
- **豁免机制**：使用文档内可见的标记，避免默认放过；被豁免处需给出原因。
- **不改变运行行为**：不修改画廊、registry、脚手架或校验逻辑；仅当文档描述与实现不符时以实现为准修文档。

## Testing Decisions

- **好测试的标准**：只断言外部可观察行为——给定一个仓库根目录（夹具或真实仓库），检查命令返回哪些问题；不断言内部解析方式。
- **唯一新增接缝**：文档一致性检查（输入根目录，输出问题列表）。已有的目录扫描接缝保持不变。
- **被测内容**：
  - 夹具仓库：引用不存在的路径 → 报错并含文档名；引用存在的路径 → 通过；命令表与脚本不一致（两个方向）→ 报错；ADR 缺状态或状态非法 → 报错；索引漏登记 ADR → 报错；豁免标记生效且无标记时不豁免；
  - 真实仓库：整理完成后检查通过（无问题）。
- **不测**：文档的措辞、排版、术语是否恰当（由评审把关）。
- **先例**：现有目录扫描测试使用临时夹具仓库并对输出做断言，同样的做法沿用；使用同一个内置测试运行器，并并入现有测试命令。

## Out of Scope

- 事件协议、组件受控化、画廊扩展点的实现（只在路线图里记录）。
- 任何组件、画廊页面、registry 输出的变更。
- 文档站点或自动生成 API 文档。
- 英文版文档（文档用中文，代码与标识符保持英文）。
- 决定库名与 registry 域名（仅标注为占位）。
- 清理死代码本身（只在架构文档里列出）。

## Further Notes

- 现状要点（写文档时的事实依据）：脚本实际为 `gen`（目录）与 `new`（脚手架），registry 生成在目录扫描里；配置文件是 JSON；meta 也是 JSON；`atoms/` 中每个文件必须登记；`deps`/`npm` 与真实 import 对照；未引用的遗留组件仍在站点目录中。
- 迁移前后 registry 对比的一次性结论已记录在 ADR-001 中，整理时保留。
- 术语表遵循「单上下文」布局：仓库根一份术语表，ADR 在文档目录。
- 本 spec 完成后，建议的下一份 spec 是「受控组件与事件协议」（路线图第一项）。
